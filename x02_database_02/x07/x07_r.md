# VIEW

## 1. VIEW 소개

### 문제
아래 쿼리(카테고리별·상태별 주문 건수)를 여러 사람이 자주 써야 한다면?
```sql
select
    p.category,
    count(*) as total_orders,
    sum(case when o.status = 'COMPLETED' then 1 else 0 end) as completed_total,
    sum(case when o.status = 'SHIPPED'   then 1 else 0 end) as shipped_total,
    sum(case when o.status = 'PENDING'   then 1 else 0 end) as pending_total
from orders o
    inner join products p on o.product_id = p.product_id
group by p.category;
```
- **복잡성:** 쓸 때마다 이 긴 쿼리를 정확히 다시 작성해야 함
- **재사용성:** 여러 곳에 복사해 두면, 로직이 바뀔 때 모든 곳을 찾아서 고쳐야 함
- **보안:** 이 쿼리를 실행하려면 원본 테이블(orders, products)에 직접 접근할 권한이 필요함
    - 운영팀 직원에게 고객 개인정보나 상품 원가 같은 민감한 정보가 담긴 원본 테이블 전체를 보여주고 **싶지 않음**

### VIEW 개념
- 실제 데이터를 가지고 있지 않은 **가상의 테이블**
- 실체는 데이터베이스에 **이름을 붙여 저장해 둔 SELECT 쿼리문** (쿼리의 바로가기)
```sql
select * from 나의_바로가기_뷰;
```

### 동작 원리
1. 사용자가 `select * from v_category_order_status;` 실행
2. DB는 `v_category_order_status`라는 실제 테이블을 찾지 않고, 이 뷰에 저장된 원래 SELECT 쿼리를 꺼냄
3. 그 쿼리를 **조회하는 그 순간에** 실행함
4. 실행 결과를 사용자에게 반환

- 데이터를 저장하지 않으므로, 원본 테이블이 바뀌면 뷰 결과도 **항상 최신 상태**로 나옴
- 참고: 결과 데이터를 실제로 저장해 두는 "구체화된 뷰(Materialized View)"도 있지만, MySQL은 지원하지 않음 (Oracle, PostgreSQL 등은 지원)

### VIEW를 쓰는 이유
- **편리성:** 복잡한 쿼리를 테이블처럼 간단히 조회
- **보안성:** 필요한 컬럼과 행만 보여줌
- **논리적 독립성:** 테이블 구조가 바뀌어도 뷰 정의만 고치면, 뷰를 쓰는 애플리케이션 코드는 바꾸지 않아도 될 수 있음 (추상화 계층 역할)

## 2. 뷰 생성, 조회, 수정, 삭제

### CREATE VIEW: 생성
```sql
create view 뷰이름 as select 쿼리문;
```

```sql
drop view if exists v_category_order_status;   -- 같은 이름의 뷰가 있으면 삭제

create view v_category_order_status as
select
    p.category,
    count(*) as total_orders,
    sum(case when o.status = 'COMPLETED' then 1 else 0 end) as completed_total,
    sum(case when o.status = 'SHIPPED'   then 1 else 0 end) as shipped_total,
    sum(case when o.status = 'PENDING'   then 1 else 0 end) as pending_total
from orders o
    inner join products p on o.product_id = p.product_id
group by p.category;
```
- 뷰 이름 앞에 `v_`를 붙이는 관례가 있음 → 테이블과 구분하기 쉬움

### SELECT: 조회
```sql
select * from v_category_order_status;
```
- 일반 테이블처럼 WHERE, ORDER BY 등을 그대로 쓸 수 있음
```sql
select * from v_category_order_status where category = '전자기기';
```

### ALTER VIEW: 수정
```sql
alter view v_category_order_status as
select
    p.category,
    sum(p.price * o.quantity) as total_sales,   -- 매출 합계 컬럼 추가
    count(*) as total_orders,
    sum(case when o.status = 'COMPLETED' then 1 else 0 end) as completed_total,
    sum(case when o.status = 'SHIPPED'   then 1 else 0 end) as shipped_total,
    sum(case when o.status = 'PENDING'   then 1 else 0 end) as pending_total
from orders o
    inner join products p on o.product_id = p.product_id
group by p.category;

select * from v_category_order_status;
```
- 계산식 컬럼에는 **반드시 별칭**을 붙이기
    - 별칭이 없으면 뷰의 컬럼 이름이 `sum(p.price * o.quantity)` 같은 식 그대로가 되어 조회하기 불편함
- 같은 역할을 하는 문법: `create or replace view 뷰이름 as ...`
    - 없으면 생성, 있으면 교체 → `drop` 후 `create` 하는 것보다 간편해서 실무에서 자주 씀

### DROP VIEW: 삭제
```sql
drop view v_category_order_status;
drop view if exists v_category_order_status;   -- 없어도 에러 없이 넘어감
```
- 뷰는 쿼리만 저장하므로, 삭제해도 **원본 테이블의 데이터는 전혀 영향을 받지 않음**

## 3. 뷰의 장점과 단점

### 장점
- **편리성과 재사용성**
    - 사용자: 쿼리 내부 로직을 몰라도 원하는 결과를 얻음
    - 개발자: 뷰 하나를 모두가 재사용. 뷰 정의만 고치면 쓰는 모든 곳에 바로 반영 → 유지보수가 쉬움
- **보안성**
    - 특정 컬럼 숨기기 (예: 원가, 개인정보 컬럼은 뷰에서 빼기)
    - 특정 행만 노출하기 (예: `where` 조건으로 특정 지역 고객만)
    - 원본 테이블 권한 없이 뷰에만 조회 권한을 줄 수 있음
    ```sql
    grant select on 쇼핑몰DB.v_category_order_status to '운영팀계정'@'%';
    ```
- **논리적 데이터 독립성**
    - 애플리케이션과 실제 테이블 구조 사이의 추상화 계층

### 단점 및 주의사항

#### 성능
- **착각:** 뷰 조회는 `select * from v_...`로 짧아 보이지만, 실제로는 저장된 무거운 쿼리가 매번 실행됨
- **최적화의 한계:** 뷰 구조가 너무 복잡하면 옵티마이저가 최적의 실행 계획을 찾기 어려움
    - **뷰 위에 또 뷰를 쌓는 방식**은 성능 저하의 주된 원인 → 가급적 피하기

#### 데이터 수정(INSERT/UPDATE/DELETE) 제약
- **수정 불가능한 뷰:** 다음이 들어간 뷰는 원본의 어느 행인지 특정할 수 없어서 수정 불가
    - 집계 함수(COUNT, SUM 등), GROUP BY, HAVING
    - DISTINCT
    - UNION / UNION ALL
    - 계산식 컬럼 (해당 컬럼 수정 불가)
    - 예: 위의 `v_category_order_status`는 GROUP BY와 집계가 있어서 수정 불가
- **수정 가능한 뷰:** 하나의 기본 테이블만 참조하고, 뷰의 컬럼이 원본 컬럼을 그대로 가리키는 단순한 뷰
    - 뷰에 INSERT/UPDATE/DELETE를 하면 **원본 테이블의 데이터가 바뀜** → 매우 주의
- **실무 규칙**
    - **뷰는 기본적으로 조회용**
    - 데이터 수정은 뷰가 아니라 **원본 테이블에 직접** 수행

---

## 4. 새로 안 것

- 뷰 = 데이터가 아니라 **이름 붙인 SELECT 쿼리**를 저장한 것 → 조회할 때마다 실행되고 항상 최신
- 뷰를 삭제하거나 수정해도 원본 데이터는 그대로
- 보안: 원본 테이블 대신 뷰에만 권한을 주면 필요한 컬럼과 행만 보여줄 수 있음
- 뷰에 계산식 컬럼을 넣을 때는 별칭 필수
- `create or replace view`로 생성과 수정을 한 번에
- 뷰는 짧아 보여도 내부 쿼리는 무거울 수 있음 → 뷰 위에 뷰 쌓지 않기
- 집계, GROUP BY, DISTINCT, UNION이 있는 뷰는 수정 불가 → 뷰는 조회용, 수정은 원본 테이블에
