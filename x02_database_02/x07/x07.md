# View

## View 소개

### 문제
```sql
select 
	p.category,
    count(*) as total_orders,
    sum(case when status = 'completed' then 1 else 0 end) as completed_total,
    sum(case when status = 'shipped' then 1 else 0 end) as shipped_total,
    sum(case when status = 'pending' then 1 else 0 end) as pending_total
from orders o
inner join products p on o.product_id = p.product_id
group by p.category;
```
- 복잡성
- 재사용성
- 보안
    - 사용자는 원본 테이블인 orders와 products에 직접 접근할 수 있는 권한이 있어야 함
    - 운영팀 직원에게는 고객의 개인정보나 상품의 원가 같은 민감한 정보가 담겨있을 수 있는 원본 테이블 전체를 보여주고 싶음

### View 개념 
- 실제 데이터를 가지고 있지 않은 가상의 테이블
- 실체는 데이터베이스에 **이름과 함께 저장된 하나의 select 쿼리문**
    - `select * from 나의_바로가기_뷰;`

### View의 동작 원리
- 사용자가 `select * from v_category_order_status;`라는 쿼리를 실행
- 데이터베이스는 `v_category_order_status`라는 이름의 실제 테이블을 찾지 않음
    - 대신, 이 뷰에 정의된 원래의 긴 `select 쿼리문`을 찾음
- 데이터베이스는 그 저장된 `select 쿼리문`을 그 순간에 실행함
- 실행 결과가 사용자에게 반환됨

### View를 사용하는 이유
- 편리성
- 보안성
- 논리적 독립성
    - 테이블의 구조가 변경되어도, 뷰의 정의만 수정하면 뷰를 사용하는 응용 프로그램은 코드를 바꿀 필요가 없을 수도 있음(추상화 계층 역할)

## 뷰 생성, 조회, 수정, 삭제

### CREATE VIEW: 뷰 생성하기
```sql
create view 뷰이름 as select 쿼리문;
```

```sql
drop view if exists v_category_order_status; -- 뷰가 이미 있을 경우 삭제

create view v_category_order_status as -- 뷰 생성
select 
	p.category,
    count(*) as total_orders,
    sum(case when status = 'completed' then 1 else 0 end) as completed_total,
    sum(case when status = 'shipped' then 1 else 0 end) as shipped_total,
    sum(case when status = 'pending' then 1 else 0 end) as pending_total
from orders o
inner join products p on o.product_id = p.product_id
group by p.category;
```

### SELECT: 뷰 조회하기
```sql
select * from v_category_order_status; -- 뷰를 사용
```

- 뷰 역시 where 절이나 order by를 사용해서 뷰의 결과를 필터링하거나 정렬할 수 있음
```sql
select * from v_category_order_status where category = '전자기기';
```

### ALTER VIEW: 뷰 수정하기
```sql
 alter view v_category_order_status as
select 
	p.category,
	sum(p.price * o.quantity),
    count(*) as total_orders,
    sum(case when status = 'completed' then 1 else 0 end) as completed_total,
    sum(case when status = 'shipped' then 1 else 0 end) as shipped_total,
    sum(case when status = 'pending' then 1 else 0 end) as pending_total
from orders o
inner join products p on o.product_id = p.product_id
group by p.category;

select * from v_category_order_status;
```

### DROP VIEW: 뷰 삭제하기
```sql
drop view v_category_order_status;
```
- 뷰를 삭제해도 원본 테이블의 데이터는 단 하나도 손상되거나 변경되지 않음

## 뷰의 장점과 단점

### 뷰의 장점
- 편리성과 재사용성
    - 사용자 입장: 쿼리의 내부 로직을 전혀 몰라도 원하는 결과를 얻을 수 있음
    - 개발자 입장: 
        - 뷰 하나만 만들어두면 모두가 재사용할 수 있음
        - 뷰의 정의만 한 번 수정하면 이 뷰를 사용하는 모든 곳에 즉시 반영되므로 유지보수성이 극적으로 향상됨

- 보안성
    - 특정 컬럼 숨기기
    - 특정 행만 노출하기

- 논리적 데이터 독립성
    - 추상화 계층 역할

### 단점 및 주의사항
- 성능 문제
    - 착각: 사용자는 자신이 매우 가벼운 쿼리를 실행한다고 착각할 수 있음
    - 최적화의 한계
        - 데이터베이스의 쿼리 옵티마이저는 매우 똑똑하지만, 뷰의 구조가 너무 복잡해지면 최적의 실행 계획을 찾아내는데 어려움을 겪을 수 있음
        - **뷰 위에 또 다른 뷰를 쌓는 방식**은 성능 저하의 주된 원인이 되므로 가급적 피해야 함

- 업데이트 제약
    - 수정 불가
    - 수정 가능
        - 뷰가 오직 하나의 기본 테이블만을 참조하고, 뷰의 모든 컬럼이 기본 테이블의 실제 컬럼을 직접 참조하는 경우에는 뷰에 데이터를 추가하거나 삭제할 수 있음
        - **단, 원본 테이블의 값이 변경되므로 매우 주의**
    - 실무 규칙
        - **뷰는 기본적으로 조회용**
        - 수정해야한다면, 뷰가 아니 원본 테이블에 직접 수행
